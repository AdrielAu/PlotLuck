Choosing where to open is a costly guess

For a small restaurant, the wrong location can sink the business. It is hard to compare areas before signing a lease, and a first-time owner rarely has more than gut feel and a few site visits.

Plotluck helps founders compare English postcode districts for the restaurant they want to open. It is built for independent founders, including people bringing under-represented cuisines to new areas.

One of our teammates watched his father’s restaurant close during COVID. We wanted to make the first location search a little less guesswork.

Plotluck is free, runs in the browser and needs no account.

A language model reads, a trained network scores

Read

A small open language model turns the description into six fields: area, cuisine, menu prices, rent, restaurant type and other requirements.

NN2 · on the user’s device

Check

Every field must quote the description as evidence. Places are matched to an offline map of England. Anything missing or unclear becomes a question.

Validator · rules, not AI

Score

A neural network trained on 130,337 English restaurants scores the profile in every district of the search area.

NN1 · trained on IBM LinuxONE

Everything runs in the browser from a static GitHub Pages site. There is no server to pay for or switch off, so Plotluck stays live after the event.

No user data is collected. The description is held only in the open tab.

Two models, one answer

In

“A mid-range Cantonese dim sum restaurant in Manchester…”

→

NN2 reads

Qwen2.5-0.5B-Instruct, open weights

  • Runs in the browser with WebLLM on WebGPU; about 288 MB, downloaded once
  • Reads up to 1,000 characters
  • Returns six fields as JSON, each with the quote it came from
  • Marks every value as stated or inferred
→

Validator

Deterministic rules

  • Rejects values not grounded in the text
  • Resolves places offline
  • Asks only for what is missing
→

NN1 scores

Neural network, 94 → 64 → 32 → 1

  • 8 restaurant inputs: cuisine, cuisine group, type, price band, chain and three dietary flags
  • 15 district inputs: population, age, ethnicity, sex, deprivation, rent, restaurant supply, attractions, hotels
  • ReLU layers, sigmoid output: a 0–1 score per district

Why a small language model? It is small enough to run on an ordinary laptop, so a founder’s plans never leave their machine.

Why a separate scorer? Scoring needs numbers learned from real outcomes. NN1 is tiny, fast and exported as plain JSON weights with a JavaScript forward pass.

Removed 1,177 without a location, 620 duplicate listings, 70 far from any postcode and 707 in districts that cross the Welsh or Scottish border.

130,337with a usable rating label

The label combines average rating, the mix of review grades and review volume, damped by 20 prior reviews so a handful of reviews cannot dominate.

How we tested it

Five-fold cross-validation with whole postcode districts held out, so the test always uses districts the model never trained on. Each fold keeps its own early-stopping slice and is compared with a baseline that always predicts the average.

District context, all open data: Census 2021 (population, age, ethnicity, sex), Indices of Deprivation 2025, Valuation Office Agency rent, OpenStreetMap attractions and hotels, and the ONS Postcode Directory.

Run results: runs/2026-10-17-train-nn1-context/metrics.json. Restaurant data: a 2021 Tripadvisor-derived dataset published on Kaggle.

We trained the model on IBM LinuxONE

  • Ingest and clean the full restaurant and district data in Jupyter on the VM.
  • Train and cross-validate NN1 on LinuxONE. The Tripadvisor-derived rows never leave the server.
  • Export the weights as JSON so the website can keep scoring after the VM expires.
  • Check byte order: weights written on a big-endian machine are load-tested on x86 before release.

A shortlist, not a promise

Data stays where it belongs

Tripadvisor-derived training rows stay on LinuxONE. We publish only model outputs, with attribution, for non-commercial use. Restaurant samples in the repo are synthetic.

Private by design

The description is read on the user’s device and held only in the open tab. Nothing is sent to a server or stored.

Asks instead of guessing

Each field must be backed by the user’s own words. Inferred values are marked, and missing or unclear details become a question.

Limits, stated plainly

The data may miss restaurants that closed. District averages cannot tell you what one street or lease will be like. Founders should visit sites and check the numbers themselves. The answer-reading AI and LinuxONE acceleration benchmark are still being tested.
